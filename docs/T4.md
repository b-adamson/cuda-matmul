# T4 baseline and profiling protocol

Status (23 October 2026): T4 profiling access was demonstrated in Colab by the
project author. The harness and protocol below are ready for a GPU run; no T4
performance results have yet been recorded in this repository. The local editing
environment has neither nvcc nor an NVIDIA GPU. Historical A6000 timings remain
in README.md. The register kernel retains the existing 64x64x8 / 4x4 design.

## Run in Colab

Select a GPU runtime, clone this repository, and change into its directory. Check
the actual allocation with `!nvidia-smi`: Colab may allocate a different GPU.
These commands assume a T4 and a CUDA toolkit with sm_75 support (CUDA 11+ is
needed for the harness's explicit cuBLAS pedantic math mode).

```bash
nvcc --version
nvidia-smi
make clean
make ARCH=-arch=sm_75
./matmul 65 all 1 1
python3 scripts/baseline.py --ncu
```

Prefix shell commands with `!` in notebook cells, or put them in a `%%bash` cell.
If `ncu` is not on PATH, locate the already installed Nsight Compute executable
and add its directory to PATH. Record its version; profiling compatibility and
counter permissions depend on the allocated runtime. A profiling failure leaves
ordinary benchmark CSVs intact and marks the overall run as failed in metadata.

For persistence, mount Google Drive through Colab's `google.colab.drive.mount`,
then use a **new** directory on the mounted drive:

```bash
python3 scripts/baseline.py --ncu --output /content/drive/MyDrive/cuda-matmul/t4-run-001
```

The runner checks N=1,7,8,9,15,16,17,63,64,65,127,128,129 before timing
N=512,1024,2048,4096. All three custom kernels handle partial tiles. They do not
return early before a block barrier. A mismatch, nonfinite result, CUDA error or
cuBLAS error fails the process. Inputs are deterministic, asymmetric, signed FP32
values generated from MT19937 seed 1. Outputs start as NaNs to catch missing writes.

Every custom output is checked against cuBLAS at every size, before and after
timing. cuBLAS uses `CUBLAS_PEDANTIC_MATH` to keep this FP32 baseline explicit.
An independent double-precision CPU oracle checks every output for N<=128 and
32 deterministic outputs (including corners) above that size, for cuBLAS and
each selected kernel before timing. This sampling supplements the full cuBLAS
comparison; it does not constitute an exhaustive independent large-size check.
The CPU tolerance is `1e-5 + 2e-5 * sum(abs(a*b))`; full cuBLAS comparison uses
`1e-3 + 2e-3 * abs(reference)` per element and relative L2 error <=2e-4.

For memory and synchronization validation, if Compute Sanitizer is available:

```bash
compute-sanitizer --tool memcheck --error-exitcode 1 ./matmul 65 all 1 1
compute-sanitizer --tool racecheck --error-exitcode 1 ./matmul 65 all 1 1
compute-sanitizer --tool synccheck --error-exitcode 1 ./matmul 65 all 1 1
```

## Timing and artifacts

`./matmul N [all|naive|tiled|regtiled|cublas [iterations [samples]]]` prints CSV
to stdout and device/correctness diagnostics to stderr. Defaults: N=1024,
10 launches per sample, 5 samples. Five warmup launches precede timing for each
kernel. CUDA events measure device execution, including gaps between launches;
allocations, copies, references and correctness checks are outside the interval.
All kernels use the default stream. Inputs and outputs are reused across launches,
so this is a repeated-GEMM workload, not a cold-cache benchmark. Small matrices can
be sensitive to launch overhead. FLOPs are counted conventionally as `2*N^3`.

The runner saves raw samples, median/min/max time and median-time TFLOP/s,
all command logs, CUDA/cuBLAS/driver versions, `nvidia-smi -q` before and after,
one-second GPU clock/power/temperature/utilization samples when supported, Git
revision/status/diff, source snapshots and SHA-256 hashes including the executable.
Record the build command and compiler output alongside these artifacts, e.g.
`make ARCH=-arch=sm_75 2>&1 | tee build.log`. Source/binary hashes identify a run
but do not independently prove how the binary was built. One-second telemetry
does not resolve the clocks of individual short kernels. Repeat complete runs to
assess clock/thermal drift and fixed kernel-order effects. No clock locking is
attempted; Colab may deny it. Record other active GPU workloads and runtime type.

Commit source, scripts and useful small CSV/metadata files to Git after review.
The runner does not commit or push. Copy large `.ncu-rep` files to persistent
external storage; they are ignored by Git. `make clean` removes only the executable,
so saved reports survive. A runtime-local result directory is temporary.

## T4 analytical starting point

NVIDIA lists 8.1 TFLOP/s FP32 and up to 320 GB/s memory bandwidth for the T4
([datasheet](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/tesla-t4/t4-tensor-core-datasheet-951643.pdf),
[product brief](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/tesla-product-literature/T4%20Product%20Brief.pdf)).
These are specification limits, not measured sustainable rates. The
[Turing tuning guide](https://docs.nvidia.com/cuda/archive/11.4.2/turing-tuning-guide/index.html)
describes 64 FP32 cores/SM, 32 resident warps/SM and 64 KiB shared memory/SM.
Check the allocated device's reported SM count (T4: 40) and clock telemetry.
For a measured SM clock f in GHz, the FP32 FMA limit is
`40 * 64 * 2 * f / 1000` TFLOP/s. At f=1.59 this is 8.1408 TFLOP/s.
Do not substitute the A6000's SM count or clock into this expression.

For square row-major GEMM with beta=0, ideal compulsory global traffic is
`12*N^2` bytes: read A and B once and write C once. Ideal intensity is `N/6`
FLOP/byte. For tile-aligned N, source-level operand request counts are:

| Kernel | Requested input bytes | Requested output bytes | Large-N intensity |
|---|---:|---:|---:|
| naive | 8*N^3 | 4*N^2 | 0.25 FLOP/byte |
| tiled, T=16 | 8*N^3/16 | 4*N^2 | 4 FLOP/byte |
| regtiled, BM=BN=64 | 4*N^3*(1/64+1/64) | 4*N^2 | 16 FLOP/byte |

The request counts describe the source algorithm, not physical DRAM bytes.
Broadcast, coalescing, cache reuse and compiler transformations change traffic
at each memory level. Multiplying these intensities by 320 GB/s yields a
no-cache request-volume estimate, not an unconditional roofline bound. Use measured
DRAM bytes for a measured DRAM roofline. Irregular sizes also have predication
and padded arithmetic costs; count useful FLOPs in reported throughput.

### Why the old shared-memory ceiling needs revision

The historical 4.84 TFLOP/s A6000 estimate assumed eight bank bytes per thread's
FMA. It is not a validated ceiling. In a 16x16 block, a warp spans two rows:
each A read addresses two distinct words broadcast to 16 lanes each; each B
read addresses 16 words duplicated across the two half-warps. Consequently,
32 threads' logical operand bytes do not map one-to-one onto bank service.
NVIDIA documents shared-memory broadcast/multicast in its
[CUDA best practices guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#shared-memory-and-memory-banks).

At source level the tiled kernel still needs two warp load instructions per
inner iteration and has one accumulator dependency chain per lane. Register
tiling reduces logical shared loads from 2 to 0.5 per FMA and adds independent
accumulators, but neither fact predicts a fourfold speedup by itself. Inspect
generated SASS and measured shared transactions, instruction issue, dependencies,
barriers, registers and occupancy before deriving a sustainable shared-memory
or instruction-throughput limit. Keep A6000 predictions as historical hypotheses.

## Profile the shared-memory hypothesis

The profiling mode launches exactly one custom kernel with no cuBLAS calls or
warmups. Run correctness separately first. The runner uses:

```bash
ncu --set full --clock-control none --cache-control all --launch-count 1 \
    --export tiled ./matmul --profile tiled 1024
```

Use a new report name for each experiment. `--clock-control none` avoids requiring
clock-control privileges; clocks remain variable. `--cache-control all` explicitly
requests cache flushing during replay. This differs from warm repeated event
timing; optionally collect a separate report with `--cache-control none` to
investigate cache sensitivity. Never compare profiler timings directly with
ordinary benchmark timings. Nsight replay and counter collection can perturb
execution ([CLI reference](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html),
[profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)).

Inspect Speed of Light, Memory Workload Analysis, Compute Workload Analysis,
Scheduler Statistics, Warp State Statistics, Launch Statistics and Occupancy.
Section/metric availability depends on Nsight version; inspect `ncu --list-sections`
and `ncu --query-metrics` instead of assuming metric names from another GPU.

| Hypothesis | Measurements to inspect | Evidence that weakens it |
|---|---|---|
| Shared-memory service saturates | shared throughput, transactions/wavefronts, bank conflicts, shared-load SASS | low shared utilization with dependency/issue stalls |
| Accumulator/load dependencies dominate | eligible warps, issue activity, short scoreboard/math dependency stalls, accumulator SASS | high relevant pipe utilization without dependency pressure |
| Barriers dominate | barrier stalls, warps eligible, phase count | little barrier waiting |
| Occupancy/register pressure dominates | registers/thread, achieved occupancy, spills/local-memory traffic | ample eligible warps and no spills |
| DRAM/cache service dominates | DRAM and L1/L2 bytes/throughput, hit rates, long scoreboard stalls | low memory utilization and execution dependency pressure |

Stall labels alone are not proof: correlate several metrics with the actual
instructions, compare sizes, and change one kernel feature at a time. Compare
naive/tiled/regtiled profiles at the same N and conditions. T4 shared throughput,
sustainable DRAM bandwidth and dominant bottlenecks remain unmeasured until those
reports exist. Register tiling, vectorization, buffering and Tensor Cores follow
only after this baseline is recorded. Turing has no Ampere-style `cp.async`;
future overlap experiments must use mechanisms supported by sm_75.
